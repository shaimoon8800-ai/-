# 会议纪要提炼官

会议开完，最不值钱的是逐字稿，最值钱的是**谁在什么时候之前要交什么**。本 Skill 把原始记录压成一页纸，把"说过的话"变成"能跟进的事"。

## 什么时候用

- 用户贴了一段会议逐字稿 / 录音转写 / 速记 / 群聊记录，要"整理一下"
- 用户会后要发纪要，或要提取待办跟进
- 用户要把历史会议记录做复盘，找"当时到底定了什么"
- 用户要输出周会/月会/评审会的标准化记录

**输入过于零碎时**（只有三两句），先问清会议主题与参与人，再决定是否值得成稿。

## 工作流（五步）

### 第 1 步 · 输入识别与清洗
按 `references/transcript-cleaning.md` 处理：

- 去掉口水（"嗯""那个""就是说"）、重复表达、打断
- 修正明显的同音字错误（"上架"误转"上架/上家"、"KPI"误转"开屁爱"）
- 标注发言人（有标注就保留；没标注则按语义推断并标注为「发言方 A/B」）
- **不删减语义**：只去噪，不改写观点

### 第 2 步 · 议题切分
把会议按讨论主题切成若干段，每段一个议题。输出议题清单：

```
议题 1 · 主题（讨论时长占比）
议题 2 · ...
```

议题外的闲聊、寒暄不进纪要（可用一句话概括为"其他"）。

### 第 3 步 · 四类信息抽取
按 `references/decision-extraction.md` 与 `references/action-items.md`：

| 类型 | 判断标准 | 缺失时 |
|---|---|---|
| **决议** | 有明确结论、且有人拍板（"就这么定""可以，按这个来") | 不写 |
| **待办** | 有动作 + 有交付物；最好有责任人和时间 | 责任人写「待确认」 |
| **风险/异议** | 有人提出反对、担忧、前提条件 | 不写 |
| **未决** | 讨论了但没结论，需要再议 | 归入"下次议题" |

**关键判定**：区分"讨论过的方案"和"定下来的方案"。讨论十轮但没拍板的，属于**未决**，绝不能当成决议写进纪要——这是会议纪要最常见的失真。

### 第 4 步 · 补齐与标注
- 待办缺责任人 → 标「待确认」
- 待办缺时间 → 标「待确认」
- 决议缺依据 → 标注"（依据：x 分钟处的数据/结论）"
- 数字、金额、日期与原文核对一遍，**原文没说的不补**

### 第 5 步 · 输出五段式

固定格式，不要自由发挥：

```markdown
# 【会议主题】会议纪要

**时间**：YYYY-MM-DD HH:MM　**时长**：xx 分钟
**参与人**：A、B、C　**记录**：（谁整理）

---

## 一、核心结论（≤5 条）
1. …
2. …

## 二、决议
| # | 决议内容 | 拍板人 | 依据 |
|---|---|---|---|

## 三、待办事项
| # | 事项 | 负责人 | 截止时间 | 依赖/备注 |
|---|---|---|---|---|

## 四、风险与异议
- ⚠️ 风险点：…　提出人：…
- ❓ 异议：…　提出人：…

## 五、未决事项与下次议题
1. [议题] —— 需要谁提供什么信息才能定
```

## 输出原则

- **一页纸优先**：超过一页的纪要不是纪要，是流水账
- **决议必须有人**：没人拍板的叫"倾向"，不叫"决议"
- **待办必须可验收**："跟进一下"不是待办，"周五前给出 3 版方案"才是
- **区分事实与观点**：事实进"结论/决议"，观点进"风险与异议"
- **保留反对意见**：未被采纳的异议也要记录，后期出问题时这是唯一的回溯依据

## 红线

- 不臆造会议中没有的决议、数据、责任人
- 不把"某人的个人看法"写成"团队共识"
- 涉及人事、薪酬、裁员、诉讼等敏感议题时，输出前提醒用户确认纪要的知悉范围
- 录音转写涉及隐私时，提醒用户遵守当地法规与公司政策

## 付费模式（支付宝 AI 按量付费 · A2M 协议）

本 Skill 为**按调用量计费**的付费技能，单次调用价格 **¥0.01**。
该单价在三处保持一致：服务端 402 账单金额、支付宝 AI 付站点登记的服务单价、以及本 Skill 的上架表单单价——三者不一致会导致用户无法完成付款。

**四步编排（Agent 侧）**

| 步骤 | 动作 | 期望结果 |
|------|------|----------|
| `probe` | 发起调用，未携带支付凭证 | 收到 `402` + `Payment-Needed`（内含账单） |
| `pay` | 把账单交给支付宝官方支付能力拉起收银 | **由用户本人完成付款**，付款后取得 `Payment-Proof` |
| `complete` | 携带 `Payment-Proof` 重试同一请求 | 服务端验付通过后交付，返回 `200` + `Payment-Validation` |
| `ack` | 交付完成后回执履约确认 | 幂等处理，同一凭证重复请求不会重复扣费 |

**前置检查**：调用前先确认运行环境具备支付宝支付能力；不具备时应明确提示用户先安装官方「支付宝 AI 付」能力，而不是让调用静默失败，更不允许退化成免费旁路。

**异常处理**

| 情况 | 状态码 | 处置 |
|------|--------|------|
| 输入非法（如无任何有效会议内容） | `400` | 必须在发出账单**之前**拦截，不因非法输入收费 |
| 收款渠道未配置 | `503` | 明确拒绝，**不得免费放行** |
| 未携带凭证 / 验付失败 / 金额不符 | `402` | 回落并重新签发账单 |
| 验付网关不可达（结果不明） | `502` + `retry_with_same_proof=true` | **不得回落 402**，否则会诱导用户重复付款 |
| 履约确认失败 | `502` | 保留交付物，允许同一凭证重试，不重造交付物 |
| 用户取消付款 | — | 终止本次调用，不产生交付 |

**安全红线**

- 不暴露付款链接、二维码、交易号等敏感信息。
- 私钥与商户配置只保存于服务端；**本 Skill 包内不含任何密钥、支付账号或收款码**。
- 免费内容仅限结构说明与元信息，不存在绕过计费的免费旁路。

**履约内容**：单次付费对应一次完整交付（五步工作流 + 五段式纪要），并完成 `ack` 回执。

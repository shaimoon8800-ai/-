# 汇报材料生成器

职场最大的浪费之一：**干了十分活，写成三分**。本 Skill 不帮你编功绩，只帮你把已经做过的事，用别人看得懂的方式讲清楚。

## 什么时候用

- 用户给了一堆零散的工作记录 / 待办清单 / 数据，要写周报、月报
- 用户要做述职报告、季度总结、项目复盘
- 用户说"这周好像没干什么""不知道怎么写才显得有成绩"
- 用户要把技术性内容翻译成给领导看的语言

**先确认三件事**：**汇报对象**（直属领导/跨部门/高层）、**汇报类型**（周报/月报/述职/项目）、**篇幅要求**（一页纸/正式报告）。

## 工作流（五步）

### 第 1 步 · 素材归位
把用户给的零散内容分成四类：

| 类别 | 说明 | 在汇报里的位置 |
|---|---|---|
| 已完成 | 有结果的 | 成果部分（重点） |
| 进行中 | 有进度的 | 进展部分 |
| 遇到的问题 | 有阻碍的 | 风险与需求部分 |
| 下步计划 | 要做的 | 计划部分 |

**注意**：用户提供的原始素材往往把"过程"和"结果"混在一起。要主动拆开——**过程是过程，结果是结果**。

### 第 2 步 · 亮点挖掘
按 `references/highlight-mining.md`，对"已完成"的部分做三件事：

```
做了什么（动作）→ 带来什么（影响）→ 用什么证明（数据）
```

| 原始说法 | 挖掘后 |
|---|---|
| 优化了后台接口 | 重构订单接口，平均响应时间从 800ms 降至 120ms，日均 3 万次调用少等待约 6 小时 |
| 做了用户调研 | 完成 20 位用户深度访谈，产出 3 个可落地的功能方向，其中 2 个已排期 |
| 整理了文档 | 把 12 份散落文档整合为一份操作手册，新同事上手时间从 3 天缩到 1 天 |

**关键**：数字必须来自用户提供的事实。用户没给数字，就写 `【请补：具体数据】`，**绝不虚构**。

### 第 3 步 · 按结构成文
按 `references/report-structures.md` 选对应结构：

| 类型 | 结构 |
|---|---|
| 周报 | 本周成果 → 进行中 → 问题与需求 → 下周计划 |
| 月报 | 目标回顾 → 关键成果（数据）→ 问题与偏差 → 下月重点 |
| 述职 | 岗位理解 → 关键成果 → 能力成长 → 不足与改进 → 下阶段规划 |
| 项目汇报 | 目标 → 进度 → 风险 → 资源需求 → 里程碑 |

### 第 4 步 · 数据表达
按 `references/data-storytelling.md`：

- 数字要**有对比**（环比、同比、目标完成率）
- 表述要**有结论**（"转化率 3.2%，高于目标 0.7 个百分点"，不是"转化率 3.2%"）
- 差距要**有归因**（"低于预期 15%，主要因 A 环节延期 5 天"）
- 不夸大：不确定的不写死，用"预计""初步"

### 第 5 步 · 自检 + 预判提问
运行 `scripts/report_lint.py`：

```bash
python3 scripts/report_lint.py --input 汇报草稿.md
```

检查：是否有成果项、是否带数据、是否有行动项、是否全是过程描述。

然后给出：

1. **领导可能追问的 5 个问题**（针对薄弱处）
2. **准备材料清单**（被问到时能立刻拿出的数据/文档）

## 输出交付物

1. 汇报正文（按结构成文，可直接交）
2. 亮点提炼对照表（原说法 → 提炼后）
3. 数据缺口清单（哪些地方需要补数字）
4. 预判提问 + 准备材料清单

## 输出原则

- **不编造成果**：只把做过的事说得更清楚，不新增没做的事
- **不夸大数字**：用户给什么写什么，缺口标出来
- **结论先行**：每段第一句就是结论，不要"因为…所以…"
- **去掉自我贬低**：不写"只是""仅仅""也没什么"，实事求是地陈述
- **也说问题**：只报喜的汇报在专业度上是减分项；把困难和需求讲清楚，更容易拿到资源

## 红线

- 不虚构业绩数据、不夸大成果、不把团队成果说成个人成果
- 不把别人的工作写进自己的汇报
- 涉及客户名称、金额、未公开业务数据时，提醒用户注意保密要求
- 不协助粉饰失误（可以客观陈述问题与改进，不可隐瞒）

## 付费模式（支付宝 AI 按量付费 · A2M 协议）

本 Skill 为**按调用量计费**的付费技能，单次调用价格 **¥0.01**。
该单价在三处保持一致：服务端 402 账单金额、支付宝 AI 付站点登记的服务单价、以及本 Skill 的上架表单单价——三者不一致会导致用户无法完成付款。

**四步编排（Agent 侧）**

| 步骤 | 动作 | 期望结果 |
|------|------|----------|
| `probe` | 发起调用，未携带支付凭证 | 收到 `402` + `Payment-Needed`（内含账单） |
| `pay` | 把账单交给支付宝官方支付能力拉起收银 | **由用户本人完成付款**，付款后取得 `Payment-Proof` |
| `complete` | 携带 `Payment-Proof` 重试同一请求 | 服务端验付通过后交付，返回 `200` + `Payment-Validation` |
| `ack` | 交付完成后回执履约确认 | 幂等处理，同一凭证重复请求不会重复扣费 |

**前置检查**：调用前先确认运行环境具备支付宝支付能力；不具备时应明确提示用户先安装官方「支付宝 AI 付」能力，而不是让调用静默失败，更不允许退化成免费旁路。

**异常处理**

| 情况 | 状态码 | 处置 |
|------|--------|------|
| 输入非法（如无任何素材） | `400` | 必须在发出账单**之前**拦截，不因非法输入收费 |
| 收款渠道未配置 | `503` | 明确拒绝，**不得免费放行** |
| 未携带凭证 / 验付失败 / 金额不符 | `402` | 回落并重新签发账单 |
| 验付网关不可达（结果不明） | `502` + `retry_with_same_proof=true` | **不得回落 402**，否则会诱导用户重复付款 |
| 履约确认失败 | `502` | 保留交付物，允许同一凭证重试，不重造交付物 |
| 用户取消付款 | — | 终止本次调用，不产生交付 |

**安全红线**

- 不暴露付款链接、二维码、交易号等敏感信息。
- 工作素材只在本地处理，**不上传任何内容到外部服务**。
- 私钥与商户配置只保存于服务端；**本 Skill 包内不含任何密钥、支付账号或收款码**。
- 免费内容仅限结构说明与元信息，不存在绕过计费的免费旁路。

**履约内容**：单次付费对应一次完整交付（五步工作流 + 四件交付物），并完成 `ack` 回执。

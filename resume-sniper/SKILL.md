# 简历狙击手

投简历没回音，九成不是能力问题，是**简历没对上 JD 的关键词**——HR 平均 7 秒扫一份，系统（ATS）更是先按关键词过筛。本 Skill 把"简历 + JD"这对输入，加工成一份**为这个岗位特制**的简历。

## 什么时候用

- 用户给了一份简历（文件或文本）和一段 JD / 岗位描述
- 用户说"帮我改简历""这份简历投这个岗位行吗""我该怎么优化简历"
- 用户要准备面试，需要针对该岗位的预测问题
- 用户同时投多个岗位，需要一稿多版

**只给了简历没给 JD**：先向用户要目标岗位信息（至少：岗位名称、职责描述、任职要求）。没有 JD 的"优化简历"是玄学，不做。

## 工作流（五步，不可跳步）

### 第 1 步 · 读入与确认
拿到两份材料后，先输出一份**材料确认清单**：简历里识别到的字段（姓名/求职意向/教育/经历/项目/技能/证书）、JD 里识别到的模块。缺关键信息（如目标岗位）就停下来问，不要猜。

### 第 2 步 · JD 拆解
按 `references/jd-parsing.md` 把 JD 拆成五层：

| 层级 | 含义 | 用途 |
|---|---|---|
| 硬性要求 | 学历、年限、必备证书、必须掌握的技术栈 | 判断是否够得着 |
| 加分项 | "熟悉…者优先""有…经验加分" | 排布内容优先级 |
| 显性关键词 | JD 原文出现的名词/工具/方法论 | 必须原词命中 |
| 隐性关键词 | 同义不同词的行业说法（JD 写"用户增长"，简历该写"拉新/留存"） | 提升匹配度 |
| 淘汰线 | 触发即被拒的硬条件（如学历门槛、行业经验） | 提前预警 |

### 第 3 步 · 简历结构化
把简历拆成可重组的积木：基本信息 / 求职意向 / 教育背景 / 工作经历（每段含职责、成果、数据）/ 项目经历（背景、动作、结果）/ 技能 / 证书 / 其他。

每条经历都标注：**是否与 JD 相关**、**是否可量化**、**是否可加动词**。

### 第 4 步 · 匹配与改写
按 `references/resume-rewrite.md` 执行：

1. 生成**关键词命中矩阵**：JD 关键词 × 简历是否命中 × 建议落点
2. 对未命中的关键词，先在用户真实经历里找对应事实；**找不到就不写**（见红线）
3. 改写经历描述：改成 `动词 + 对象 + 方法 + 量化结果` 的句式
4. 排序：与 JD 强相关的经历上移，弱相关的压缩
5. 删减：与岗位完全无关的内容（除非是唯一亮点）

### 第 5 步 · 交付四件套

必须按以下格式输出，不要自由发挥：

#### ① 命中矩阵

| JD 关键词 | 层级 | 简历命中 | 建议落点 |
|---|---|---|---|
| … | 硬性/加分 | ✅ / ❌ | 哪段经历、怎么写 |

命中率：`命中数 / 总数 = xx%`（脚本可算，见 `scripts/keyword_hit.py`）

#### ② 定制简历（Markdown 全文）
可直接复制投递的完整版本，不是"建议你这样改"。

#### ③ 缺口清单
未命中的关键词 → 对应差距 → 两种处置：`可补（用户有事实没写）` / `真缺（建议补充经历或换岗位）`。

#### ④ 面试预测 10 题
按 `references/interview-predict.md` 生成，每题附：**考察意图** + **回答框架**（不代写答案，给结构）。必含 2 题针对"简历里的薄弱点"。

## 输出原则

- **改写 ≠ 编造**：只在用户已有事实上换表达方式，不新增经历、不抬高职级、不拉长任职时间
- **数字必须用户提供**：不知道的量化结果，用占位符 `【请填：具体数值】` 标出，绝不替用户发明
- **不写空话**："精通""熟练掌握""有较强的沟通能力"这类无依据标签，一律替换为可验证的事实
- **一岗一版**：同时投多个岗位时，输出多版并标注各自的取舍逻辑

## 红线

- 不协助伪造学历、工作经历、任职时间、项目经历
- 不代写虚假在职证明、背调材料
- 用户要求"随便编点数据"时，明确拒绝并说明：背调和面试追问会当场露馅，风险远大于收益
- 涉及具体企业的内部信息、薪酬机密时，提醒用户注意保密义务

## 付费模式（支付宝 AI 按量付费 · A2M 协议）

本 Skill 为**按调用量计费**的付费技能，单次调用价格 **¥0.01**。
该单价在三处保持一致：服务端 402 账单金额、支付宝 AI 付站点登记的服务单价、以及本 Skill 的上架表单单价——三者不一致会导致用户无法完成付款。

**四步编排（Agent 侧）**

| 步骤 | 动作 | 期望结果 |
|------|------|----------|
| `probe` | 发起调用，未携带支付凭证 | 收到 `402` + `Payment-Needed`（内含账单） |
| `pay` | 把账单交给支付宝官方支付能力拉起收银 | **由用户本人完成付款**，付款后取得 `Payment-Proof` |
| `complete` | 携带 `Payment-Proof` 重试同一请求 | 服务端验付通过后交付，返回 `200` + `Payment-Validation` |
| `ack` | 交付完成后回执履约确认 | 幂等处理，同一凭证重复请求不会重复扣费 |

**前置检查**：调用前先确认运行环境具备支付宝支付能力；不具备时应明确提示用户先安装官方「支付宝 AI 付」能力，而不是让调用静默失败，更不允许退化成免费旁路。

**异常处理**

| 情况 | 状态码 | 处置 |
|------|--------|------|
| 输入非法（如未提供 JD） | `400` | 必须在发出账单**之前**拦截，不因非法输入收费 |
| 收款渠道未配置 | `503` | 明确拒绝，**不得免费放行** |
| 未携带凭证 / 验付失败 / 金额不符 | `402` | 回落并重新签发账单 |
| 验付网关不可达（结果不明） | `502` + `retry_with_same_proof=true` | **不得回落 402**，否则会诱导用户重复付款 |
| 履约确认失败 | `502` | 保留交付物，允许同一凭证重试，不重造交付物 |
| 用户取消付款 | — | 终止本次调用，不产生交付 |

**安全红线**

- 不暴露付款链接、二维码、交易号等敏感信息。
- 私钥与商户配置只保存于服务端；**本 Skill 包内不含任何密钥、支付账号或收款码**。
- 免费内容仅限结构说明与元信息，不存在绕过计费的免费旁路。

**履约内容**：单次付费对应一次完整交付（上述五步工作流 + 四件套输出），并完成 `ack` 回执。
